# Bunker Monitor — Frontend

Фронтенд (React) для системы мониторинга бункера ГОК на базе радарного уровнемера УЛМ-3D-64.

## Этап 1 — MVP (выполнен)

- Каркас приложения: Vite + React 18 + TypeScript strict
- Мок-сервер (Node/Express) с генерацией правдоподобных 64-лучевых замеров
- Панель показаний: средний/мин/макс уровень, объём, масса, время замера, статус online/offline
- **Радиальная сетка лучей** («звезда»: 8 осей A–H × 8 позиций): цветовая кодировка по высоте, честная индикация недостоверных лучей (приглушение + штриховка + тултип), подписи осей A–H крупным белым шрифтом
- **Таблица 8×8** (ось × позиция) — отображается постоянно, без переключателя вида; тултип при наведении рендерится через портал в `<body>` (`position: fixed`), поэтому не вызывает скролл таблицы ни по одной из осей и переворачивается влево/вверх у краёв экрана
  > Отклонение от исходного плана: изначально планировался переключатель «Радиальный вид / Таблица» (один вид за раз). По ходу разработки решили показывать оба вида одновременно (радиальная сетка ниже, таблица — сразу под панелью показаний) — удобнее для диспетчерской, переключатель убрали
- Сводка: достоверных / деградировано / отключено + боковые зоны
- Статус-бар: связь, время обновления, режим MOCK
- Skeleton-загрузка и ErrorMessage для всех панелей
- Live-обновление через polling каждые 1.5 с (настраивается)

## Этап 2 — История и графики (выполнен)

- Страница «История»: графики min/avg/max уровня, масса/объём (Recharts), переключатель периода (сутки/неделя/месяц)
- Экспорт выборки в CSV
  > Отклонение от исходного плана: изначально планировалась ещё и видимая таблица замеров с пагинацией (`/measurements`) на странице «История». По решению пользователя от неё отказались — таблица не показывается, доступ к данным только через «Выгрузить CSV» (сам эндпоинт `/measurements` при этом работает и используется программно для формирования CSV)

## Этап 3 — 3D-модель бункера (выполнен)

- 3D-сцена (`react-three-fiber` + `@react-three/drei`): усечённый конус бункера из `/geometry` (или резервной формы), орбитальная камера, сетка-пол, оси, высотные метки-масштаб
- **Heatmap-поверхность руды**: интерполяция высот по 64-точечной радиальной сетке (`lib/interpolateSurface`) — недостоверные лучи не «тянут» поверхность, а заполняются по соседям (азимут + радиус), с фолбэком на среднее по достоверным при полном отказе оси
- Маркеры лучей в 3D с тем же статусным кодированием, что и в 2D (сфера = достоверен, каркасный октаэдр = недостоверен — форма, не только цвет), тултип по наведению/выбору
  - Высота маркера/подписи недостоверного луча берётся из того же интерполированного грида, что и поверхность (`buildSurfaceGrid`), а не жёстко из `0` — иначе точка «проваливалась» на дно бункера, заметно ниже фактического уровня поверхности прямо над ней (исправлено)
- **Подписи имён лучей** (`A1`, `H4`...) всегда видны над каждым маркером в 3D — белым моноширинным шрифтом, крупнее при наведении/выборе луча
- **Маркер датчика УЛМ-3D-64**: положение из `/geometry.sensor` (`x, y, z`) + визуализация угла наклона `tilt_deg` — пунктирная линия истинной вертикали и сплошная линия реального наклона датчика от неё. Азимут наклона API не отдаёт (только величину угла), поэтому наклон визуализируется поворотом вокруг одной оси — это упрощение, зафиксировано в открытых вопросах. Только графический маркер, без текстовой подписи. Фолбэк-положение датчика (`FALLBACK_SENSOR` в `config/`) — когда `/geometry` недоступен
- **Синхронизация 2D↔3D**: клик по лучу в радиальной сетке или таблице подсвечивает его в 3D-сцене и наоборот (общее состояние `selectedBeam` поднято в `DashboardPage`)
- 3D-сцена вынесена в отдельный чанк (`React.lazy`) — three.js не попадает в основной бандл
- **Раскладка дашборда**: панель показаний + таблица лучей — сверху (таблица видна постоянно); радиальная сетка и 3D-модель — в отдельном ряду ниже, бок о бок, одинаковой высоты (50% высоты области дашборда)

## Этап 4 — Налипания на боковых стенках (выполнен)

- **Новый эндпоинт `/buildup`**: анализ по 8 осям — `severity` (`none`/`low`/`medium`/`high`, список открытый), `score`, `deviation_m`, `affected_positions`. Реальный критерий детекции ещё определяется заказчиком (см. открытый вопрос №4) — фронт трактует `severity`/`score`/`threshold_m` как непрозрачные значения от бэкенда и **не хардкодит пороги** ни в `lib/`, ни в компонентах
- **Мок-эвристика** (`mock-server/index.cjs`, `computeBuildupZones`): для каждой оси — линейная экстраполяция профиля высоты по внутренним позициям (1..5), сравнение факта на внешних позициях (6..8) с ожиданием; положительное отклонение сверх порога = подозрение на налипание. Один из бункеров всегда демонстрирует медленно нарастающее налипание на одной оси (для наглядности), см. `buildupLevel`/`buildupAxis` в состоянии мока — это демонстрационная генерация данных, не часть алгоритма детекции
- **`BuildupPanel`** (новая панель на дашборде): список осей, отсортированный по убыванию серьёзности, индикатор — цвет **и** иконка/форма (○/△/▲/✕ — не только цвет, для дальтоников), отклонение в метрах, задетые позиции. Неизвестные будущие значения `severity` не отбрасываются — попадают в список с пометкой «Неизв.: …» и ранжируются выше `high` (чтобы не потерять новый тип аномалии)
- **Индикатор в радиальной сетке** (`RadialBeamGrid`): для осей с `severity !== 'none'` — полупрозрачная дуга вдоль внешней зоны оси (от позиции `OUTER_ZONE_POSITION_THRESHOLD` до 8) цветом серьёзности, рисуется позади точек-лучей (не перекрывает высотную цветовую шкалу); плюс маленькая иконка серьёзности под подписью оси
- `lib/buildupUtils.ts` — только презентационные хелперы (`severityColorClasses`, `severityIcon`, `severityLabel`, `severityRank`, `sortZonesBySeverity`), никакой детектирующей логики на фронте

## Этап 5 — Алерты, здоровье Edge-узлов, мультибункер (выполнен)

- **Роутинг (`react-router-dom`)**: `bunker_id` теперь часть URL — `/` (обзор всех бункеров), `/bunkers/:bunkerId` (дашборд), `/bunkers/:bunkerId/history` (история). Это было заложено ещё на этапе 2 («роутинг добавляется на этапе 5») — заменяет независимые локальные селекторы бункера, которые раньше жили отдельно в `DashboardPage` и в `HistoryPage`. Неизвестный `bunkerId` в URL → редирект на `/`. Переключение между бункерами — через карточки на обзорном экране (см. ниже); отдельного переключателя бункера в шапке нет — алерты в шапке всегда общие по всем бункерам, а не по текущему выбранному, поэтому UI рядом с ними не должен намекать на фильтрацию по одному бункеру
- **Обзорный экран** (`features/overview/OverviewPage`): карточка на каждый бункер (online/offline, средний уровень/объём/масса, сводка достоверности лучей, худшая серьёзность налипаний) со ссылкой на дашборд этого бункера; отдельный блок здоровья Edge-узлов (`/health`: online/offline, CPU/RAM/диск, время последнего пульса) — раньше `/health` был реализован на бэкенде/моке, но нигде не отображался на фронте
- **Алерты** (`features/alerts/`): синтезируются на фронте из уже загруженных данных (не отдельный ресурс API) — `lib/alerts.ts` (`computeAlerts`), чистая функция без побочных эффектов:
  - Edge PC offline (`/health`) — критический
  - Бункер offline (`/bunkers`) — критический
  - Налипание (`/buildup`, severity ≠ `none`) — `low` → предупреждение, `medium`/`high`/**любое нераспознанное будущее значение** → критический (fail-safe: лучше перебдеть с неизвестным severity, чем молча его проигнорировать)
  - Деградация лучей выше порога (`DEGRADED_BEAM_RATIO_ALERT_THRESHOLD = 30%` в `config/`, допущение, см. открытые вопросы) — предупреждение
  - Сканирование идёт по **всем** бункерам одновременно (`useAllLatestMeasurements`/`useAllBuildup` на `useQueries`, тот же кэш React Query, что и у одиночных хуков дашборда), не только по открытому в данный момент
  - **Колокольчик с счётчиком** (`AlertsBell`) в шапке — раскрывающийся список (`AlertsPanel`), клик по алерту с `bunkerId` ведёт на дашборд этого бункера
  - **Тосты** (`ToastContainer` + `useAlertToasts`): всплывают при появлении нового алерта (по стабильному `id`, не при каждом опросе), автоматически исчезают через 8 с (`ALERT_TOAST_DURATION_MS`); если условие исчезло и возникло снова — тост появится повторно
  - Индикатор серьёзности — иконка **и** цвет (⛔/△), не только цвет, консистентно с уже принятым правилом для статусов лучей и налипаний
- **Общий `summarizeBeamHealth`** (`lib/parseMeasurement.ts`) — вынесен из `BeamHealthBar`, переиспользуется и в `BeamHealthBar`, и в карточках `OverviewPage` (было бы дублирование одной и той же агрегации достоверности лучей)
- Задел под будущую аутентификацию/роли: ничего не внедрено (по требованию ТЗ — не блокировать, но и не делать заранее), но структура (роутинг, отдельный `Header`, `Layout`) не мешает добавить экран логина/защищённые маршруты позже

### Известная уязвимость зависимости (принято осознанно)

`react-router-dom@7.18.2` — `npm audit` показывает high-severity advisory «RSC Mode CSRF Bypass» (диапазон 7.12.0–8.3.0). Уязвимость специфична для режима React Server Components/server actions — этот проект чисто клиентский SPA (Vite, без SSR, без RSC, без serverActions), этот код-путь не используется в принципе. Более старые версии (6.x, 7.11.0) содержат другие high/moderate advisories (XSS в SSR-гидратации, open redirect) с тем же обоснованием неприменимости, поэтому выбрана последняя версия. Зафиксировано как принятый риск, не блокирующий работу.

## Быстрый старт

### 1. Установить зависимости

```bash
# Фронтенд
npm install

# Мок-сервер
cd mock-server && npm install && cd ..
```

### 2. Запустить мок-сервер

```bash
# В отдельном терминале:
npm run mock
# → http://localhost:3001
```

### 3. Запустить фронтенд

```bash
npm run dev
# → http://localhost:5173 (обзор бункеров) → выберите бункер → /bunkers/:id (дашборд)
```

### Переключение на реальный FastAPI

В файле `.env` замените:

```
VITE_API_BASE_URL=http://your-backend-host:8000
VITE_MOCK_MODE=false
```

Контракт API описан ниже в разделе «API».

## Переменные окружения

| Переменная | По умолчанию | Описание |

## Открытые вопросы / Допущения

| # | Вопрос | Текущее допущение |
|---|--------|------------------|
| 1 | Единица `volume` | Принято: м³ — нужно подтверждение заказчика |
| 2 | Единица `mass` | Принято: тонны (т) — нужно подтверждение |
| 3 | Азимут оси A и направление отсчёта | Принято: A=0° (восток), против часовой. Уточняется из данных Конфигуратора — **не захардкожено**, берётся из `/geometry` |
| 4 | Критерий детекции налипаний | Определяется заказчиком. Реализовано на этапе 4: `/buildup` отдаёт `severity`/`score`/`deviation_m`/`threshold_m`, мок использует placeholder-эвристику (линейная экстраполяция профиля оси), фронт трактует значения как данные от бэкенда, не пересчитывает и не хардкодит порог |
| 5 | Тип bunkera | Сейчас: усечённый конус (`truncated_cone`). Другие формы — не реализованы |
| 6 | Высота точки геометрии (`beams[].z` в `/geometry`) | Мок всегда отдаёт `z: 0` (горизонтальная база); 3D-поверхность строится из `beam.height` замера, а не из `geometry.z`. Если у реального бэкенда `z` несёт смысл (базовая отметка точки), потребуется сложить его с `height` — сейчас не суммируется, зафиксировать при появлении реального `/geometry` |
| 7 | Резервная форма бункера (3D) | Когда `/geometry` недоступен: `FALLBACK_BUNKER_SHAPE` в `config/` (конус 7/4.2/8 м, согласовано с радиусом резервной раскладки лучей) — только для разработки |
| 8 | Азимут наклона датчика (`sensor.tilt_deg`) | API отдаёт только величину угла наклона, без направления (азимута). В 3D-визуализации (`SensorMarker`) наклон условно показан поворотом вокруг одной оси — при появлении реального `/geometry` уточнить, нужен ли отдельный параметр азимута наклона |
| 9 | Порог алерта «деградация лучей» | Принято: >30% из 64 лучей недостоверны (`DEGRADED_BEAM_RATIO_ALERT_THRESHOLD` в `config/`) — нужно подтверждение заказчика. В отличие от критерия налипаний, эта метрика считается полностью на фронте (уже парсит статусы каждого луча), поэтому порог — фронтовая константа, а не значение от бэкенда |

## Тестирование

- **Unit-тесты `lib/`** (P1): `parseStatus`, `isBeamReliable`, `parseBeamName`, `heightToColor`, форматтеры, CSV-экспорт, `dateUtils`, `geometryUtils`, `interpolateSurface`, `buildupUtils`, `alerts` (`computeAlerts`).
- **Компонентные тесты** (P2): `BeamHealthBar`, `PeriodSummary`, `VesselPanel`, `StatusBar`, `HistoryPage` (bunkerId из маршрута, редирект на неизвестный бункер), `BuildupPanel`, `AlertsPanel`, `OverviewPage`, `useAlertToasts` (через `renderHook` + `vi.useFakeTimers`), стек `@testing-library/react` + `@testing-library/user-event` + `jest-dom`.
- React Query хуки в тестах `HistoryPage`/`OverviewPage` мокируются напрямую (`vi.mock('../../api/hooks', ...)`), без `QueryClientProvider`; там, где нужен реальный роутинг (`HistoryPage`, `AlertsPanel`, `OverviewPage`) — оборачиваются в `MemoryRouter`.
- **Итого: 165 тестов, все зелёные.** 3D-сцена (Canvas/WebGL) не покрыта компонентными тестами — jsdom не рендерит WebGL; проверена вручную в браузере (Playwright-скриншоты + проверка консоли).
- `BeamTable` (тултип, скролл) и `BeamMarkers`/`SensorMarker` (высота маркеров, наклон датчика) также не имеют отдельных компонентных тестов — правки в них проверялись вручную через Playwright (наведение на все 64 ячейки/лучи, проверка `scrollWidth`/`scrollHeight` контейнера, скриншоты).
