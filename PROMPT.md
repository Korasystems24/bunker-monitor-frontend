## 0. Контекст проекта

Мы разрабатываем программно-аппаратный комплекс (ПАК) для мониторинга бункера на
горно-обогатительном предприятии. В бункер поступает руда мелкого дробления. Система
решает две задачи:

1. **Контроль общего уровня / объёма / массы руды** в бункере, включая остатки в
   боковых зонах (это главная научная новизна — конкуренты меряют в основном по
   центральной оси).
2. **Детектирование налипаний руды на боковые стенки** бункера.

Измерения даёт многолучевой радарный уровнемер **УЛМ-3D-64** (64 луча). Edge-вычисления
выполняются на промышленном мини-ПК (Intel NUC 7i5DN). Бэкенд — **Python + FastAPI +
PostgreSQL/TimescaleDB**. Данные на сервер идут через RabbitMQ; фронтенд читает их через
REST.

**Твоя зона ответственности — только фронтенд (React).** Бэкенд-эндпоинты ещё не
зафиксированы: ты проектируешь контракт API сам (см. раздел 3) и до появления реального
бэкенда работаешь против мок-сервера, который тоже создаёшь.

### Условия эксплуатации (влияют на UI/UX)
- Промышленная среда, операторская. Интерфейс смотрят с обычных мониторов и, возможно,
  с настенной панели — нужен читаемый, контрастный, «диспетчерский» вид.
- Высокая запылённость/вибрация на объекте → часть лучей регулярно приходит с
  деградированным статусом. **Корректная визуализация «плохих» лучей — это не край
  случай, а норма.** UI обязан честно показывать, каким лучам можно доверять.
- Время отклика системы по ТЗ ≤ 1 с. Интерфейс не должен добавлять заметных задержек.

### Стек и требования
- **React** (TypeScript обязателен), Vite.
- Состояние сервера: **TanStack Query (React Query)** для опроса/кэширования.
- Графики 2D: **Recharts** (или ECharts, если понадобится больше контроля — обоснуй
  выбор в README).
- 3D (на этапе 3+): **Three.js** через **react-three-fiber** + **@react-three/drei**.
- Стили: Tailwind CSS. Тёмная тема по умолчанию (диспетчерская).
- Линт/формат: ESLint + Prettier. Без отключения правил «чтобы собралось».

## 1. Что уже известно про данные

Бэкенд отдаёт замеры в таком формате (реальный пример ответа, постранично):

```json
{
  "total": 33,
  "limit": 50,
  "offset": 0,
  "items": [
    {
      "id": 33,
      "ts": "2026-05-06T22:00:30.626176Z",
      "avg_level": 2.414841957171603,
      "mass": 11.322,
      "volume": 12.5869427488409,
      "beams": [
        { "beam_name": "A1", "height": 2.6199588421751168, "status": "TooShort, NotUsed, WeakSignal" },
        { "beam_name": "H6", "height": 0,                  "status": "Unknown, NotUsed, Disabled, DistanceNotUpdating" },
        { "beam_name": "H5", "height": 2.438401774309848,  "status": "TooLong, NotUsed, WeakSignal" }
        /* ... всего 64 луча на один замер ... */
      ]
    }
    /* ... массив замеров, новый замер = новый элемент items ... */
  ]
}
```

### Критически важные особенности формата (НЕ пропусти)

1. **`status` — это строка с флагами через запятую**, а не массив и не enum. Пример:
   `"TooShort, NotUsed, WeakSignal"`. Нужно парсить: `split(",").map(s => s.trim())`.
   Известные на сегодня флаги (список открытый, не падай на незнакомых):
   - `Unknown`, `NotUsed`, `Disabled`, `DistanceNotUpdating`
   - `WeakSignal`, `TooShort`, `TooLong`, `OutOfReposeAngle`
   Сделай TypeScript-тип как `string`-union известных флагов + допускай произвольные
   строки (`(KnownFlag | string)[]`).

2. **`height` = 0 часто означает «нет валидного измерения»**, а не «руды нет».
   Смотри на статус: если есть `Disabled` / `DistanceNotUpdating` / `NotUsed` — высоту
   нельзя интерпретировать как реальную. Введи функцию `isBeamReliable(statusFlags)` и
   используй её везде.

3. `avg_level` — средний уровень, м. `volume` — объём (предположительно м³),
   `mass` — масса (предположительно тонны). **Единицы измерения подтверди в README как
   допущение и не хардкодь подписи — заведи константы.**

4. `ts` — ISO-8601 UTC. На фронте показывай в локальном времени, но храни/сравнивай в UTC.

5. **`beam_name`** — буква + цифра (`A1`, `H6`, `H5`...). Это адрес луча в **радиальной**
   раскладке датчика:
   - **буква = ось/спица**, всего 8 осей `A…H`, расходящихся из центра по азимуту
     (полный конус 90°, оси через 45°);
   - **цифра = позиция точки вдоль оси от центра к стенке**, по 8 позиций на каждой оси
     (`1` — ближе к центру, `8` — ближе к боковой стенке);
   - итого 8 × 8 = **64 луча**.
   Сделай парсер `parseBeamName("H6") → { axis: "H", position: 6 }` и обратное
   сопоставление. **Внешние позиции (большие цифры) = боковые зоны бункера** — это
   ключевые точки для детекции налипаний (этап 4).
   Физические координаты точек в самих замерах НЕ приходят — они задаются геометрией
   (см. раздел 4).

> ⚠️ Файл-образец `data.txt`, который дал заказчик, **обрезан** (заканчивается на середине
> массива beams первого замера). Не считай его полным — это иллюстрация схемы. Опирайся
> на описание выше.

## 2. Референс конкурента (что брать, что улучшить)

У конкурента (вьювер Limaco УЛМ-3D) интерфейс выглядит так:
- слева — **панель показаний сосуда**: Product, Density, Volume, Mass, Min/Avg/Max Level;
- центр — **сетка пронумерованных лучей** с цветовой кодировкой по высоте (красный →
  синий шкала) + текстовое значение в метрах на каждой ячейке;
- центр/право — **3D-вид бункера** с цветной поверхностью руды (heatmap по высоте);
- цветовая легенда диапазонов высоты справа;
- статус-бар внизу: состояние связи, режим, статусы уровнемеров.

**Что берём:** общую раскладку (панель показаний + сетка лучей + 3D), цветовую
кодировку по высоте, текстовые значения на ячейках, статусную строку.

**Что делаем лучше:**
- Честная индикация недостоверных лучей (у конкурента видно «No communication / All
  Levelmeters offline» — но статусы отдельных лучей теряются). У нас статус каждого луча
  должен быть виден сразу (иконка/штриховка/тултип).
- Современный отзывчивый UI, тёмная тема, адаптив под широкий монитор.
- Акцент на **боковые зоны и налипания** (наша фишка по ТЗ), а не только центр.
- История с графиками min/max/avg за сутки/неделю/месяц (требование ТЗ).

## 3. Контракт API (спроектируй и зафиксируй)

Бэкенда ещё нет. Предложи REST-контракт под FastAPI, согласованный с форматом из раздела 1,
и **сразу реализуй мок-сервер**, отдающий такие ответы, чтобы фронт разрабатывался
автономно. Заложи мультибункерность в URL с самого начала (даже если бункер пока один).

Предлагаемая отправная схема (уточни/дополни и опиши в `API.md`):

```
GET  /api/v1/bunkers
     → [{ "id": "bunker-1", "name": "Бункер №1", "online": true,
           "geometry_id": "geom-default" }]

GET  /api/v1/bunkers/{bunker_id}/measurements/latest
     → один объект-замер (как item из раздела 1) — для live-дашборда

GET  /api/v1/bunkers/{bunker_id}/measurements?from=&to=&limit=&offset=
     → постраничный список замеров (как в data.txt: total/limit/offset/items)

GET  /api/v1/bunkers/{bunker_id}/stats?period=day|week|month
     → { "period": "...", "min_level": .., "max_level": .., "avg_level": ..,
         "series": [{ "ts": "...", "avg_level": .., "mass": .., "volume": .. }] }
     (требование ТЗ: min/max/avg за сутки/неделю/месяц)

GET  /api/v1/bunkers/{bunker_id}/geometry
     → описание геометрии бункера и раскладки 64 лучей (см. ниже)

GET  /api/v1/health
     → { "edge_pcs": [{ "node_id": "edge-1", "online": true, "last_pulse": "...",
         "cpu": .., "ram": .., "disk": .. }] }   // для алертов «Edge PC offline»
```

Требования к мок-серверу:
- лёгкий (Node/Express или статический json-server — на твой выбор, обоснуй);
- генерирует правдоподобные 64-лучевые замеры с реалистичным разбросом статусов
  (часть лучей деградирована — это норма, см. раздел 1);
- эмулирует поток: `latest` меняется во времени, history накапливается;
- умеет эмулировать «Edge PC offline», чтобы проверить алерты.
- README объясняет, как запустить фронт против мока и как потом переключить на реальный
  FastAPI (через `VITE_API_BASE_URL`).

## 4. Геометрия лучей и бункера — РАДИАЛЬНАЯ модель (уточнено заказчиком)

Раскладка лучей **радиальная**, а не прямоугольная сетка:

- Уровнемер УЛМ-3D-64 стоит сверху и излучает **8 осей (спиц) A…H**, расходящихся из
  центра по азимуту (полный конус 90°, оси примерно через 45°).
- На каждой оси — **8 точек измерения (позиции 1…8)** от центра к стенке. Итого 64 луча.
- **Координаты каждой точки (x, y, z или азимут+радиус+высота установки) рассчитывает
  Конфигуратор** (поставляется с оборудованием) на этапе пусконаладки — из габаритов
  бункера, координат установки уровнемера и угла его наклона. У каждого бункера своя
  раскладка.

### Жёсткие правила для фронта
- **Фронт НЕ вычисляет геометрию лучей.** Координаты приходят с бэкенда (из Конфигуратора)
  через `GET /geometry`. Фронт их только потребляет и рисует. Не реализуй расчёт раскладки
  из габаритов — это ответственность Конфигуратора/бэкенда.
- Если `/geometry` недоступен (например, при работе только против мока без раскладки) —
  фронт использует **fallback-раскладку по умолчанию**: 8 осей через 45°, 8 равномерных
  позиций по радиусу, плоское дно. Это резерв для разработки, не продакшн.
- Ожидаемый ответ `/geometry` (предложи и зафиксируй в `API.md`):

```json
{
  "bunker_id": "bunker-1",
  "shape": { "type": "truncated_cone", "top_diameter_m": .., "bottom_diameter_m": .., "height_m": .. },
  "sensor": { "x": .., "y": .., "z": .., "tilt_deg": .. },
  "beams": [
    { "beam_name": "A1", "axis": "A", "position": 1, "x": .., "y": .., "z": .. },
    { "beam_name": "A2", "axis": "A", "position": 2, "x": .., "y": .., "z": .. }
    /* ... 64 точки с координатами от Конфигуратора ... */
  ]
}
```

### Представление лучей в UI (вместо сетки 8×8)
- Основной вид сетки лучей — **полярный/радиальный** («звезда»): 8 спиц по азимуту,
  по 8 точек на каждой, как на компоновочной схеме датчика. Цвет точки — по высоте,
  достоверность — по статусу.
- Дополнительно дай **табличный вид** (ось × позиция, 8×8 таблица значений) для инженера —
  это удобно для чтения чисел, но геометрически это просто матрица, не план бункера.
- В README отметь как допущение: точное соответствие азимутов осям (A=0°? направление
  отсчёта, по/против часовой) уточняется по данным Конфигуратора; не зашивай жёстко,
  бери из координат в `/geometry`.

## 5. Этапы работы

Делай по порядку. После каждого этапа: проект собирается (`npm run build`), запускается
(`npm run dev`), линт чистый, и в README описано, что готово. Не забегай вперёд.

### Этап 1 — MVP: каркас + панель показаний + таблица лучей  ⭐ приоритет

Цель MVP — оператор открывает дашборд (без логина) и видит текущее состояние бункера:
сводные показания и **таблицу/сетку замеров по всем 64 лучам с цветовой кодировкой и
статусом**. Это самое важное для заказчика.

1. Инициализация проекта: Vite + React + TS + Tailwind + ESLint/Prettier. Структура папок
   (`api/`, `components/`, `features/`, `lib/`, `config/`, `types/`).
2. Типы данных (`types/`): `Measurement`, `Beam`, `BeamStatusFlag`, `BunkerStats`,
   `BunkerInfo`, `BunkerGeometry`, `Health`. Утилиты: `parseStatus()`, `isBeamReliable()`,
   `parseBeamName("H6") → { axis, position }`, форматтеры единиц/времени.
3. Мок-сервер (раздел 3) + слой API на fetch + React Query хуки (`useLatestMeasurement`,
   `useBunkers` и т.д.). Live-обновление через polling (интервал в конфиге, по умолчанию
   ~1–2 с, согласовано с ТЗ ≤1 с отклика).
4. **Панель показаний сосуда**: Min/Avg/Max Level, Volume, Mass, время последнего замера,
   индикатор online/offline бункера. Аккуратные единицы измерения из констант.
5. **Сетка/таблица 64 лучей** — ядро MVP:
   - основной вид — **полярная/радиальная раскладка** («звезда»): 8 осей A–H по азимуту,
     по 8 точек на каждой, координаты берутся из `/geometry` (fallback — равномерная
     радиальная раскладка, см. раздел 4);
   - каждая точка: `beam_name`, высота (м, формат), цвет по высоте (шкала как у
     конкурента: красный=высоко → синий=низко), легенда диапазонов;
   - **недостоверные лучи визуально отделены**: приглушение + штриховка/иконка, тултип
     со списком флагов статуса; такие точки не участвуют в цветовой шкале высоты;
   - переключатель «Радиальный вид / Таблица»: альтернативный вид — таблица 8×8
     (ось × позиция) со значениями и статусом, сортируемая, для инженера;
   - агрегаты: сколько лучей валидно / деградировано / отключено, и отдельно сводка по
     внешним позициям (боковые зоны).
6. **Статус-бар** внизу: связь с бэкендом, время последнего успешного запроса,
   режим (live/мок).
7. Состояния загрузки/ошибки/пустых данных для всех панелей (skeleton + понятные
   сообщения, не «белый экран»).
8. README: запуск, переменные окружения, что в MVP готово, открытые вопросы (точные
   единицы измерения volume/mass, ориентация азимутов осей A–H, критерий налипаний).

**Критерий готовности MVP:** при запущенном моке открывается дашборд, видны сводка и
радиальная раскладка из 64 лучей с корректной раскраской и честными статусами; «плохие»
лучи явно помечены; данные сами обновляются.

### Этап 2 — История и графики (требование ТЗ)

1. Страница/вкладка «История».
2. Графики **min / avg / max уровня** + масса/объём за период **сутки / неделя / месяц**
   (Recharts), переключатель периода, использование `/stats`.
3. Таблица замеров с пагинацией (`/measurements`, формат total/limit/offset).
4. Экспорт выборки в CSV.

### Этап 3 — 3D-модель бункера (Three.js / r3f)

1. 3D-сцена бункера (форма из `/geometry`), орбитальная камера, оси/масштаб.
2. **Поверхность руды**: интерполяция высот по 64 точкам радиальной раскладки (координаты
   из `/geometry`, с учётом достоверности — недостоверные лучи не «тянут» поверхность;
   опиши метод интерполяции в коде, для радиальных данных уместна интерполяция по
   азимуту+радиусу) → цветная heatmap-поверхность по высоте, как у конкурента, с легендой.
3. Маркеры лучей в 3D с тем же статусным кодированием, тултипы.
4. Синхронизация: клик по лучу в сетке (этап 1) подсвечивает его в 3D и наоборот.

### Этап 4 — Налипания на боковых стенках (наша научная фишка по ТЗ)

1. Отдельный слой/режим визуализации боковых зон бункера.
2. Подсветка зон со подозрением на налипание. Опора — аномалии высот на **внешних
   позициях спиц (большие цифры в beam_name, ближе к стенкам)** относительно ожидаемого
   профиля; конкретный критерий — параметр, уточняется с заказчиком; заложи интерфейс
   под него.
3. Панель/список зон с налипаниями + индикатор серьёзности.
   > Метрику/алгоритм детекции налипаний на бэкенде ещё определяют — фронт должен уметь
   > принять её как поле в API и отрисовать; не зашивай конкретный порог в компоненты.

### Этап 5 — Алерты, здоровье Edge-узлов, мультибункер

1. Панель/тосты алертов: «Edge PC offline», «налипания», «бункер offline»,
   «деградация лучей выше порога» (использование `/health`).
2. Переключатель/обзор нескольких бункеров (URL и состояние уже мультибункерные с
   этапа 1 — здесь добавляем UI выбора и общий обзорный экран).
3. (Опционально) подготовка под будущую аутентификацию/роли — но НЕ внедрять в этих
   этапах, только не мешать будущему добавлению.

## 6. Общие правила для Claude Code

- **Спрашивай, не выдумывай.** По открытым вопросам (ориентация азимутов осей A–H,
  единицы измерения, критерий налипаний, точные имена эндпоинтов) делай разумное
  дефолтное допущение, **выноси его в конфиг** и фиксируй в README в разделе «Открытые
  вопросы / Допущения». Не прячь допущения внутри компонентов. Раскладку лучей и
  координаты фронт НЕ вычисляет — берёт из `/geometry` (см. раздел 4).
- Архитектура **multi-bunker-ready** с первого коммита (bunker_id в роутинге и API),
  даже пока бункер один.
- TypeScript strict. Никаких `any` для данных API — описывай типы.
- Никакого браузерного `localStorage/sessionStorage`, если это будет работать как
  артефакт; для обычного веб-приложения — обычные практики, но состояние сервера держи
  в React Query, не дублируй вручную.
- Декомпозиция: мелкие переиспользуемые компоненты; бизнес-логика (парсинг статусов,
  достоверность, цветовые шкалы, интерполяция) — в `lib/`, не в JSX.
- Каждый этап заканчивается рабочей сборкой и обновлённым README. Коммить по этапам.
- Производительность: 64 луча × частый polling — нормально, но не делай лишних
  ре-рендеров (мемоизация сеток, выбор интервала опроса в конфиге).
- Доступность и читаемость: цвет не единственный носитель информации о статусе луча
  (дублируй иконкой/паттерном) — важно для диспетчерской и дальтоников.
