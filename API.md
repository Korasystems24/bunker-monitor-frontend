# API-контракт — Bunker Monitor

Контракт реализован реальным Python/FastAPI backend и мок-сервером (`mock-server/index.cjs`).
Frontend использует `VITE_API_BASE_URL` с версионным префиксом, например
`http://localhost:8000/api/v1`, и добавляет к нему пути ресурсов без повторного `/api/v1`.

Базовый префикс — `/api/v1`. Все ответы — JSON. `bunker_id` — часть пути везде, где ответ относится
к конкретному бункеру (multi-bunker-ready с первого коммита, см. `CLAUDE.md`).

Соответствующие TypeScript-типы — в `src/types/index.ts`, здесь только форма ответов и пояснения.

---

## GET /api/v1/bunkers

Список бункеров.

```json
[
  { "id": "bunker-1", "name": "Бункер №1", "online": true, "geometry_id": "geom-bunker-1" },
  { "id": "bunker-2", "name": "Бункер №2", "online": true, "geometry_id": "geom-bunker-2" }
]
```

`online` — агрегированный статус связи с этим бункером (в моке завязан на общий Edge PC, у реального
бэкенда с несколькими Edge-узлами может отличаться по бункерам).

## GET /api/v1/bunkers/:bunker_id/measurements/latest

Последний замер — для live-дашборда (поллинг раз в `POLL_INTERVAL_MS`, по умолчанию 1.5 с).

```json
{
  "id": 4213,
  "ts": "2026-07-29T07:21:00.000Z",
  "avg_level": 2.61,
  "min_level": 1.35,
  "max_level": 3.96,
  "volume": 13.82,
  "mass": 31.796,
  "beams": [
    { "beam_name": "A1", "height": 2.62, "status": "" },
    { "beam_name": "H6", "height": 0, "status": "Unknown, NotUsed, Disabled, DistanceNotUpdating" }
  ]
}
```

Критически важно (см. открытые вопросы в README, №1–2):
- `status` — строка через запятую, не массив: `split(',').map(s => s.trim())` (`lib/beamUtils.ts:parseStatus`).
- `height = 0` **не значит «руды нет»**, если статус содержит `Disabled`/`DistanceNotUpdating`/`NotUsed`/`Unknown`
  — проверять `isBeamReliable(statusFlags)` (`lib/beamUtils.ts`), никогда не читать `height` напрямую.
- `min_level`/`max_level` в самом замере — это мин/макс **высот отдельных лучей** этого замера (по
  достоверным лучам), не то же самое, что `avg_level`.
- Единицы: `avg_level`/`min_level`/`max_level` — метры, `volume` — м³ (допущение), `mass` — тонны
  (допущение, плотность 2.3 т/м³) — константы в `src/config/index.ts` (`UNITS`, `DENSITY_T_PER_M3`),
  не хардкодить подписи.
- `ts` — ISO-8601 UTC. Хранить/сравнивать в UTC, показывать в локальном времени (`formatTimestamp`).
- `avg_level`/`min_level`/`max_level`/`volume`/`mass` и `beams[].height` могут быть `null`;
  frontend показывает отсутствие значения как `—`, а луч с `height: null` считает недостоверным.

## GET /api/v1/bunkers/:bunker_id/measurements?from=&to=&limit=&offset=

Постраничный список замеров (используется фронтом только программно — для CSV-экспорта на странице
«История», см. открытые/принятые решения в README про отсутствие видимой таблицы замеров).

```json
{
  "total": 2000,
  "limit": 50,
  "offset": 0,
  "items": [
    {
      "id": 4213,
      "ts": "2026-07-29T07:21:00.000Z",
      "avg_level": 2.61,
      "min_level": 1.35,
      "max_level": 3.96,
      "volume": 13.82,
      "mass": 31.796
    }
  ]
}
```

Элементы списка намеренно не содержат `beams`; детальные 64 луча отдаёт только `/latest`.
Числовые поля могут быть `null`. `from`/`to` — ISO-8601, опциональны.

## GET /api/v1/bunkers/:bunker_id/stats?period=day|week|month

Агрегаты для графиков истории.

```json
{
  "period": "day",
  "min_level": 0.47,
  "max_level": 5.96,
  "avg_level": 3.14,
  "series": [
    {
      "ts": "2026-07-29T06:00:00.000Z",
      "avg_level": 2.9,
      "min_level": 1.2,
      "max_level": 4.1,
      "mass": 38.2,
      "volume": 16.6
    }
  ]
}
```

Бакетирование по времени (в моке): 1 ч для `day`, 6 ч для `week`, 1 день для `month`. `min_level`/
`max_level` в точках серии берутся из мин/макс высот лучей внутри бакета, а не из `avg_level` —
иначе при одном замере на бакет три линии графика совпадали бы.

## GET /api/v1/bunkers/:bunker_id/geometry

Геометрия бункера и раскладка 64 лучей — **фронт её не вычисляет**, только потребляет (см. открытый
вопрос №3 и №5–7 в README: азимут оси A, тип формы, `beams[].z`; вопрос №8 про азимут наклона
датчика закрыт — см. описание `sensor` ниже).

```json
{
  "bunker_id": "bunker-1",
  "shape": {
    "type": "tiered_rect",
    "bottom_x_m": 1.8, "bottom_y_m": 2.4, "bottom_height_m": 0,
    "middle_x_m": 2.4, "middle_y_m": 2.4, "middle_height_m": 1.4,
    "top_x_m": 3.2, "top_y_m": 3.2, "top_height_m": 2.0,
    "vessel_height_m": 3.4,
    "full_volume_m3": 23.85,
    "rotation_deg": 0
  },
  "sensor": { "x": 1.2, "y": -1.2, "z": 3.2, "tilt_x_deg": -41.6, "tilt_y_deg": 41.3 },
  "beams": [
    { "beam_name": "A1", "axis": "A", "position": 1, "x": 0.35, "y": 0, "z": 0 }
    /* ... 64 точки ... */
  ]
}
```

**Модель сосуда — `shape` (тип `tiered_rect`, из Конфигуратора)**: прямоугольный в плане
резервуар, сужающийся через три уровня сечения — `bottom` → `middle` → `top`, у каждого свои
независимые ширины по X и Y (это не тело вращения: X и Y на одном уровне могут различаться, как
у `bottom_x_m: 1.8` / `bottom_y_m: 2.4` в примере выше). Поля каждого уровня:
- `{level}_x_m`, `{level}_y_m` — полная ширина сечения по X/Y на этом уровне, м (сечение
  центрировано по осям X/Y, т.е. простирается от `-{level}_x_m/2` до `+{level}_x_m/2`);
- `{level}_height_m` — отметка (Z) этого уровня от дна сосуда (`bottom_height_m` обычно `0`).

Дополнительные поля:
- `vessel_height_m` — полная высота сосуда (отметка верхнего края/крыши).
- `full_volume_m3` — справочная полная ёмкость сосуда от Конфигуратора; фронт её не использует
  для расчёта объёма руды (это делает `measurement.volume`), только показывает как метаданные,
  если потребуется.
- `rotation_deg` — поворот прямоугольного сечения сосуда вокруг вертикальной оси (OZ),
  **всегда кратен 90°**. Координаты лучей (`beams[].x/y`) уже учитывают реальную ориентацию
  установки — фронт не пересчитывает их при повороте, поворачивает только визуальную оболочку
  сосуда в 3D-сцене (`BunkerShape`).

**Важно про форму стенки в 3D:** по референсному вьюверу Конфигуратора видимая форма сосуда —
ровно две части, снизу вверх:
1. простой прямоугольник (без сужения/расширения) от `bottom_height_m` до `middle_height_m`,
   постоянной ширины `bottom_x_m` × `bottom_y_m`;
2. одна прямая трапеция выше него, от `middle_height_m` до `vessel_height_m` (верх сосуда),
   расширяющаяся от той же ширины `bottom_x_m` × `bottom_y_m` (стык без ступеньки) до
   `top_x_m` × `top_y_m` у самого верха.

`middle_x_m`/`middle_y_m`/`top_height_m` для этой стенки **не используются** — `BunkerShape` в
3D строит форму ровно по `bottom_*`, `middle_height_m`, `top_x_m`/`top_y_m` и `vessel_height_m`.
Остальные поля фронт хранит и передаёт как часть контракта (могут понадобиться бэкенду для
расчёта объёма/страппинг-таблицы), но в самой геометрии стенки бункера не участвуют.

Форма зафиксирована как единственная поддерживаемая на проде (см. открытый вопрос №5 в
README) — раньше рассматривался `truncated_cone`, но фактическая модель сосуда, которую отдаёт
Конфигуратор, — `tiered_rect`; фронт не поддерживает других значений `type`.

Если `/geometry` недоступен — фронт использует резервную раскладку (`FALLBACK_GEOMETRY`/
`FALLBACK_BUNKER_SHAPE`/`FALLBACK_SENSOR` в `src/config/index.ts`): 8 осей через 45°, равномерный
радиус лучей и `FALLBACK_BUNKER_SHAPE` той же формы `tiered_rect` — **только для разработки**,
не для продакшена. На проде размеры сосуда всегда приходят через бэкенд (`/geometry`), фронт их
не хардкодит.

**Датчик — `sensor` (позиция + наклон уровнемера, вкладка «Levelmeters» Конфигуратора)**:
- `x`, `y`, `z` — положение уровнемера в системе координат бункера, м. `z` отсчитывается от того
  же дна, что и `shape.*_height_m`/`vessel_height_m` (в примере выше уровнемер стоит чуть ниже
  крыши: `z=3.2` при `vessel_height_m=3.4`, т.к. крепится через крышу и слегка выступает внутрь).
- `tilt_x_deg`, `tilt_y_deg` — наклон луча визирования от истинной вертикали, уже разложенный
  Конфигуратором по осям X и Y самого бункера (`incl_x`/`incl_y` в UI Конфигуратора). Это закрывает
  прежний открытый вопрос №8 в README: раньше API отдавало только величину наклона без азимута
  (`tilt_deg`), теперь наклон задан двумя перпендикулярными компонентами — направление наклона
  полностью определено, ничего не нужно предполагать на фронте. Это показания двухосевого
  инклинометра: каждый угол — это угол между лучом и истинной вертикалью, если смотреть на
  *проекцию* луча на одну вертикальную плоскость (X/высота или Y/высота) — независимо от второго
  угла. `SensorMarker` в 3D восстанавливает сам вектор луча напрямую через тангенсы обоих углов
  (`direction ∝ (tan(tilt_x), −1, tan(tilt_y))` в системе бункера), а НЕ двумя последовательными
  поворотами по осям — последовательные повороты компонуются друг с другом и не воспроизводят
  исходные углы проекции, если оба угла заметны (могут даже развернуть эффективный наклон по одной
  из осей на противоположный знак). Прочие поля Конфигуратора на этой вкладке (`α`/`β`/`γ`, `θ`,
  `Levelmeter Radius`, `Height above the Roof`) — внутренние параметры калибровки самого устройства;
  `/geometry` их не отдаёт, фронту нужны только уже посчитанные `tilt_x_deg`/`tilt_y_deg`.

## GET /api/v1/bunkers/:bunker_id/buildup

Анализ подозрения на налипание руды на боковых стенках по каждой из 8 осей (этап 4).

```json
{
  "bunker_id": "bunker-1",
  "ts": "2026-07-29T07:21:00.000Z",
  "threshold_m": 0.35,
  "zones": [
    {
      "axis": "C",
      "severity": "high",
      "score": 1,
      "deviation_m": 1.17,
      "affected_positions": [7, 8]
    }
    /* ... по одной записи на каждую из 8 осей, включая severity: "none" ... */
  ]
}
```

**Критично:** `severity` (`none`/`low`/`medium`/`high`, список открытый — как и флаги статуса луча),
`score`, `deviation_m` и `threshold_m` — фронт трактует как непрозрачные значения от бэкенда.
Реальный критерий детекции определяется заказчиком (открытый вопрос №4 в README); мок использует
placeholder-эвристику (линейная экстраполяция профиля оси, см. `mock-server/index.cjs:computeBuildupZones`).
Фронт **не** пересчитывает и не хардкодит порог ни в одном компоненте — см. `lib/buildupUtils.ts`.

## POST /api/v1/debug/edge-offline (только мок-сервер)

Не часть контракта с реальным бэкендом — служебный эндпоинт мока для ручной проверки алерта
«Edge PC offline» без ожидания реального сбоя.

```bash
curl -X POST http://localhost:3001/api/v1/debug/edge-offline \
     -H "Content-Type: application/json" \
     -d '{"online": false}'
```

## Выбор технологии мок-сервера

Node/Express, а не `json-server` — потому что нужна не статичная выдача фикстур, а живая генерация:
реалистичный разброс статусов лучей (`pickStatus`), дрейф уровня во времени, накапливающаяся история
(`setInterval`), демонстрационное нарастание налипания на одной оси, ручное управление состоянием Edge PC
(`/debug/edge-offline`) — весь этот процедурный код проще писать на обычном сервере, чем настраивать
поверх `json-server` middleware/generators. Express выбран как самый распространённый и лёгкий вариант,
без ORM/фреймворка — сервер укладывается в один файл (`mock-server/index.cjs`) без отдельной сборки.
